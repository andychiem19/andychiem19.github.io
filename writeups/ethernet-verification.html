Overview

My first project at Woodward McCoach Inc., meant to enable high-speed Ethernet design verification for hobbyists or as an alternative to expensive Ethernet verification IPs. Primarily a software networking project that required deep understanding of the Physical Layer (Layer 1) of the OSI Networking Model.

The existing development was done for CAUI-4, a 100G 4-lane electrical interface commonly used in optical telecom, carrying a line rate of 25.78125G (data + overhead) across each of four lanes and NRZ modulation.

The goal was a reusable, standards-driven source of 100G traffic that could exercise the MAC end-to-end in simulation. Refer to IEEE 802.3 Clause 82/83 for specifications.

Transmit path

Each stage below was developed following loose coupling design principles, allowing for rigorous unit and integration testing.

  1. Packet generation
  2. Virtual MAC
  3. 64b/66b encoding
  4. Scrambling
  5. Lane distribution
  6. AM insertion
  7. DCMAC interface

Packet generation & Virtual MAC

Scapy was used to generate Ethernet packets, and a virtual MAC layer adds the preamble, enforces the interframe gap and computes the frame check sequence, so every frame entering the PCS is valid Ethernet.

PCS: encoding, scrambling, distribution

The PCS, or Physical Coding Sublayer is responsible for processing data for high-speed Ethernet transmission. Frames are split into 64-bit blocks and prepended with a 2-bit sync header.

That data is then scrambled using a self-synchronizing scrambler (to preserve DC electrical characteristics and facilitate clock and data recovery), and distributed across 20 virtual PCS lanes.

To support lane deskew and alignment on the receiving side, encoded alignment markers are inserted every 16383 66-bit blocks.

# Not source code; example of a self-synchronizing scrambler implementation
def scramble(block: int, state: int) -> tuple[int, int]:
    out = 0
    for i in range(64):
        bit = ((block >> i) ^ (state >> 38) ^ (state >> 57)) & 1
        state = ((state << 1) | bit) & ((1 << 58) - 1)
        out |= bit << i
    return out, state

Verification approach

Healthy software design principles, like loose coupling and code reuse, allowed for effective and accurate initial software development. I was able to apply directed and constrained random tests at nearly every level to reduce hardware debugging work needed later down the line.

e.g. A key constrained-random test I did was the generation of packets with randomized fields and payloads, from length 64 to 1500, interleaving the four transmission lanes into a software script that rasterizes and checks for valid Ethernet traffic.

I used Wireshark on .pcap files to verify my Ethernet packet generator and virtual MAC, and ultimately integration tested in cocotb using my custom Ethernet stimulus to lock up an Ethernet MAC (Versal DCMAC Subsystem), checking data on the other side.

Takeaways

A key purpose this project served early on was allowing me to demo common optical telecom themes in software. Data in optical telecommunications is frequently encoded, scrambled, marked, and interleaved/de-interleaved to various widths, and implementing them in software while reading about the theory behind Ethernet allowed me to understand, early on, why and how data is moved digitally.

Another key takeaway was comfortability working from a spec. IEEE 802.3 is quite verbose, and extracting the necessary elements to create my own Ethernet protocol taught me to understand what's important, and by extension the underlying reasoning present in every spec.

Beyond the code, I documented the project's standards and progress so future developers can extend the environment, hopefully to include a comprehensive set of 100G, 400G, and OTN protocols, after my co-op.
