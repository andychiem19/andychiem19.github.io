Debugging an AXI-Lite Performance Monitor

Resolved differing behavior in simulation and hardware using Vivado ILAs; increased bandwidth measurements from 70% to 100% of expected.

Problem

A new addition to the IP library, our AXI-Lite Performance Monitor, had recently been tested on a variety of our boards' AXI-Lite interfaces. The performance monitor had returned reasonable test results on all our boards, except one (let's call it board X), where it was reading about 70% of the expected bandwidth.

This could mean one of two things:

  1. Board X's AXI-Lite interface was genuinely running at 70% of the rated bandwidth
  2. An issue exists in the Performance Monitor IP that only emerged on one board

Preliminary testing revealed that data wasn't being lost on board X's AXI-Lite interface, so it was most likely running at expected bandwidth, leading me to focus on the second possibility.

Investigation

I started with hardware testing through our software for controlling the boards, running sets of commands to configure the snapshot interface and simulate an AXI-Lite link for long enough to monitor it over a given snapshot size.

On 4G PRBS testing, I replicated the previous results after inserting and building board X with the performance monitor embedded.

However, when I moved to the 50G 100GAUI test that had returned lower than expected results, I got unreasonably low bandwidth numbers, even lower than prior tests had found, in the range of 10% to 50% efficiency. Prior testing had shown about 60%, while expected efficiency was about 83%.

This led me to find several issues in the RTL via ILA debugging and a simulation I developed, detailed in the diagram below.

Root cause

The performance monitor was experiencing an off-by-one error in hardware testing that couldn't be replicated in software, likely partially related to a bad gating/timing RTL practice.

Notably, this fix to the IP did not address the initially low bandwidth found in previous testing, which was found to be a testing error. When the snapshot interface was initialized properly the fixed performance monitor reliably returned the expected bandwidth. However, this debugging still allowed me to discover a critical error in our IP and make it robust for future AXI-Lite testing.

Fix and results

I added a pipeline register to separate the add and 32-bit compare into two cycles, and unnested the stop trigger condition so it would always check again after the count settled. I tested this extensively in simulation using directed and constrained random testing, before testing in hardware with ILAs and our board control software.

After fixing our test procedure and reinforcing our Performance Monitor IP, I achieved readings of about 103Gbit/s, or the expected 83% efficiency.

Takeaways

My key takeaway was that hardware testing is crucial, precisely because simulation can only approximate concurrent behavior. The bug in the Performance Monitor IP depended on a hardware timing edge case that I couldn't hit with directed tests at all, even when I built testbenches specifically to attempt to replicate the error. It's a good reminder that simulation narrows the search, but doesn't prove correctness.
